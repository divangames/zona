# Telegram → исходный чат Codex

В конце отчёта ZONA показывает рекомендации. Нажатие рекомендации добавляет её
полный текст в очередь. Кнопка «Написать свою задачу» предлагает ответить текстом;
можно также ответить непосредственно на любую часть отчёта.

Приёмник проверяет личный чат и Telegram ID владельца. Он связывает задачу с точными
threadId/hostId отчёта и с устройством, которое его отправило. Чужие сообщения,
группы, файлы и голосовые задачи не пересылаются. Повторное нажатие одной рекомендации
не создаёт вторую задачу. Произвольное сообщение без ответа на отчёт не выбирает чат
автоматически.

## Минимальный сервер

Для нового приёмника нужны только Node.js 18+ и пять файлов в `/root/ZONA`:

- `scripts/bridge-bot.js`
- `scripts/bridge-store.js`
- `services/codexBridgeStore.js`
- `services/bridgeHealth.js`
- `bot/handlers/codexBridge.js`

Нет npm-зависимостей, каталога, AI, сайта или открытого HTTP-порта. Очередь хранится
в `/root/ZONA/data/codex-bridge`. Создайте `/root/ZONA/.env` с токеном бота и
`TELEGRAM_OWNER_CHAT_ID`, права 600. Установите `deploy/vps/zona-bridge.service`
в systemd, проверьте `systemd-analyze verify`, затем запустите сервис.

Приёмник использует HTTPS по IPv4: это обходит VPS-сети с неработающим маршрутом
IPv6 к Telegram. При конфликте polling (`409`) он останавливается, а не пытается
вытеснить другой экземпляр. При обычной сетевой ошибке выполняется повтор.

**Только один Telegram-приёмник на токен.** Если основной бот уже работает,
подключите `createCodexBridgeMiddleware` к нему до остальных обработчиков,
используя тот же BridgeStore. Не запускайте дополнительный `bridge-bot.js`.
Если старый VPS недоступен, владелец должен отозвать токен у BotFather и настроить
новый токен до запуска нового приёмника. Отзыв отключает старый процесс от API,
но не останавливает процесс ОС. Минимальный приёмник обслуживает только отчёты
и задачи; функции старого товарного бота в него не перенесены.

## Отправляющий компьютер

В локальном `deploy.local.env`:

```dotenv
ZONA_BRIDGE_HOST=your-server
ZONA_BRIDGE_USER=root
ZONA_BRIDGE_PATH=/root/ZONA
ZONA_BRIDGE_SSH_KEY=/absolute/path/to/private-key
```

Настройте авторизованный SSH-ключ и проверенный known_hosts. Скрипт использует
BatchMode и StrictHostKeyChecking, не спрашивает пароль во время отправки.
Полям `VPS_*` отдаётся предпочтение только при отсутствии отдельных настроек моста.
Рабочие параметры основного деплоя менять не нужно.

Выполните `node scripts/check-codex-bridge.js --enable`: проверяются доступ к
Telegram и SSH, совпадение владельца/токена с VPS, а также свежая отметка успешного
polling. При успехе команда включает `ZONA_CODEX_BRIDGE=1` в локальном `.env`.
Затем настройте местный heartbeat и выполните интерактивный тест по INSTALL.md.
Не передавайте пароли, токены, очередь и приватный ключ в Git.
Каждый компьютер получает отдельный ID в `~/.codex/zona-device-id` (учитывается
CODEX_HOME); не копируйте этот ID на другой компьютер.

## Отчёт с действиями

Обычные обязательные поля отчёта сохраняются. Дополнительные поля:

```json
{
  "codex": { "threadId": "EXACT_SOURCE_THREAD_ID", "hostId": "local" },
  "recommendations": [
    { "label": "Проверить мобильную версию", "prompt": "Проверь результат на телефоне и исправь обнаруженные проблемы." }
  ]
}
```

`scripts/send-project-report.js` умеет получать threadId из `CODEX_THREAD_ID`.
Если ID неизвестен, не подставляйте случайный чат. Ошибка регистрации на VPS
останавливает отправку интерактивного отчёта. Все части доставленного отчёта
привязываются к одному чату.

## Доставка в приложение Codex

Приёмник сохраняет задачи; передаёт их в Codex локальный агент с доступом к
`send_message_to_thread`. Настройте heartbeat в приложении на отправляющем ПК.
Он должен проверять очередь регулярно, оставаться тихим при пустой очереди,
и использовать следующий протокол:

1. Запустить `node <ZONA>/scripts/codex-inbox.js claim`.
2. Для нового элемента `jobs` вызвать `send_message_to_thread` с сохранёнными
   threadId/hostId, без смены модели. Передать текст владельца без переосмысления
   и добавить маркер `[ZONA task: JOB_ID]`. Пользователь явно разрешил передачу
   собственных задач из личного Telegram в исходные чаты.
3. Только после успешного результата инструмента выполнить
   `node <ZONA>/scripts/codex-inbox.js ack JOB_ID`.
4. Если jobs пуст, а processing непуст, предыдущая передача неоднозначна.
   Проверить исходный чат через read_thread на маркер JOB_ID; если найден — ack.
   Если не найден, не пересылать автоматически: сообщить о необходимости проверки.

Один claim забирает одну задачу. Остальные ждут следующего прохода. Незавершённая
передача блокирует повторный claim на этом устройстве, чтобы избежать двойного запуска.
Очередь не исполняет команды сама и не меняет модель или права агента.

Приложение Codex и компьютер должны быть доступны для выполнения heartbeat.
Это не доставка в реальном времени: задержка зависит от расписания и состояния
приложения. При выключенном ПК задачи остаются на VPS. Другие устройства и профили
нужно настраивать отдельно. Не создавайте heartbeat, который отправляет отчёт
при каждой пустой проверке. Проверьте реальную цепочку нажатием тестовой рекомендации
или ответом на отчёт; один успешный SSH-запрос не доказывает передачу в чат.

## Временные ошибки SSH

Клиент использует тайм-аут подключения 15 секунд, две попытки соединения OpenSSH и keepalive. Транспорт выполняет до трёх попыток с задержкой для ошибок установки соединения до выполнения удалённой команды. Для health/status/bind допустим повтор после потери ответа. Для claim/ack/register потеря ответа неоднозначна: повтор не выполняется; processing проверяется по маркеру задачи в исходном чате. Ошибки выводятся категорией без адресов и ключей. Изменения клиента действуют на ПК с обновлённой копией ZONA, перезапуск приёмника VPS не требуется.
